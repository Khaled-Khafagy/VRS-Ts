## Report Format

Two files are always generated together:
1. `Group_Plan_Test_Execution_Report.md` — raw data source (markdown)
2. `Group_Plan_Test_Execution_Report.html` — visual export with charts (opened in browser after generation)

Both live in the project root: `/Users/khafagy/Desktop/VRS-new/VRS-Ts/`

---

## HTML Report Structure

### Header
- Background: Vodafone Red `#E60000`, white text
- Left: Report title + "Travel eSIM · Pre-Production · vrs.preprod.travel.vodafone.com"
- Right: Report Date, Sprint (PI / SP / Fix Version), Scope (cycles count + test cases count + exclusions note)

### KPI Cards (8 cards in a grid)
1. Total Test Cases
2. Executed (with %)
3. Not Executed (with %)
4. Cycles Done
5. Cycles In Progress
6. Cycles Not Started
7. Web Bugs count
8. Mobile Bugs count

### Charts (6 charts using Chart.js CDN)
1. **Overall Execution** — Doughnut (Executed vs Not Executed)
2. **Cycle Status** — Doughnut (Done / In Progress / Not Executed)
3. **Execution by Platform** — Stacked Bar (Web, Android, iOS, Email)
4. **Execution by Folder** — Horizontal Stacked Bar (one bar per folder)
5. **Web Bugs by Status** — Doughnut (all status categories)
6. **Mobile Bugs by Status** — Doughnut (all status categories)

### Tables with inline progress bars
- **Folder Summary Table**: Folder | Cycles | Total Tests | Executed | Not Executed | Progress (bar) | Cycle Status
- **Per-folder Cycle Detail tables** (one table per folder): Key | Cycle Name | Tests | Progress (bar) | Status badge
- **Web Bugs table**: Key | Summary (with priority icon prefix) | Assignee | Status badge
- **Mobile Bugs table**: Key | Summary | Assignee | Status badge
- **Infrastructure Blocker**: Red alert box at the bottom if a critical bug exists

### Status Badges (color-coded)
- ✅ DONE: green background
- 🔄 IN PROGRESS: amber background
- ⛔ NOT EXECUTED: red background
- NEW: blue background
- UNDER REVIEW: purple background
- READY FOR QA: green background
- QA IN PROGRESS: amber background
- ANALYSIS: purple background
- DISCARDED: grey background
- CRITICAL: red border + red background (used for infrastructure blockers)

### Priority icons in bug tables
- High: ▲ red
- Medium: ● amber
- Low: ▼ blue

## Data Sources

### Test Cycle Data
- Pulled from **Zephyr Scale** in Jira (project key: `TE`)
- Navigate to: Tests → Test Cycles → PI08 → SP01 → TE_R_10.0.41 → Group Plan subfolder
- Capture per cycle: Key, Name, Tests count, Progress %, Status
- Screenshots from Zephyr are acceptable input if MCP tool access is unavailable

### Bug Data
- Two separate Jira fix versions:
  - **TE_R_10.0.41** → Web bugs (navigate to Releases → TE_R_10.0.41)
  - **TE_Mobile_10.0.41** → Mobile bugs (navigate to Releases → TE_Mobile_10.0.41)
- Capture: Key, Summary, Assignee, Status, and version summary totals (Done / In Progress / To Do)
- Note: some bugs (e.g. TE-1451) appear in BOTH versions — count as 1 unique bug

## Scope Rules

- **Always exclude**: Group Plan E2E cycles (folder "Group plan E2E")
- **Always include**: purchase flow, Admin user view, secondary user view folders
- Report total cycles and total test cases in header and KPI cards after exclusions
- Note exclusions explicitly in report header scope line

## Generation Workflow

1. Gather cycle data from Zephyr (screenshots or MCP tool)
2. Gather bug data from both Jira fix version pages (screenshots or MCP tool)
3. Write/update `Group_Plan_Test_Execution_Report.md` with raw data
4. Write/update `Group_Plan_Test_Execution_Report.html` with full visual report
5. Run `open Group_Plan_Test_Execution_Report.html` to preview in browser

**Why:** User wants consistent, professional HTML reports with charts and Vodafone branding for sprint reporting. The MD file serves as the data source and the HTML is the shareable artifact.
**How to apply:** Always generate both files. Always open the HTML after generation. Never generate just the markdown alone unless explicitly asked.
